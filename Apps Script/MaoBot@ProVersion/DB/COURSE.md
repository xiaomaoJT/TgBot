#### 🎟 XiaoMaoBot · ProVersion 数据表说明

> 一共 **8 张工作表**。其中 4 张与官方版完全兼容（可直接沿用旧数据），
> 4 张为 ProVersion 新增，运行 `initDatabase()` 会自动创建。

##### 初始化

```text
不需要手工建表！
在 Apps Script 编辑器里运行 initDatabase() 即可全部自动创建。
它只对「本次新建」的表写入表头，绝不会覆盖你已有的数据。
```

---

##### ① db_telegram —— 消息存储表

> 机器人自动写入，**无需任何操作**。

| 列 | 字段 | 说明 |
|:--:|:-----|:-----|
| A | 发起时间 | `yyyy/MM/dd HH:mm:ss` |
| B | 用户ID | Telegram 数字 ID |
| C | 用户名称 | `@username`，无则为「🈚️用户名」 |
| D | 用户昵称 | 显示名 |
| E | 消息类型 | 群聊消息 / 私聊消息 / 入群事件 / 敏感词触发删除 … |
| F | 消息来源 | 群名 + 会话类型 |
| G | 来源ID | 群/会话 ID（超级群以 `-100` 开头） |
| H | 消息内容 | 文本或 `[类型] 说明` |
| I | 消息JSON | 原始 update（可在设置里关闭以节省空间） |
| J | 消息ID | 用于批量删除 / 追溯 |

> 前 3 行为表头，**数据从第 4 行开始** —— 与官方版保持一致，旧数据可直接沿用。
>
> ⚠️ 建议定期清理。可在 `Params.gs` 设置 `CONFIG.storage.keepDays` 让系统自动清理。

##### ② key_params —— 关键字回复表

> 用于配置关键字自动回复。支持无限多条，支持多段文本连续发送。

| 列 | 字段 | 必填 | 说明 |
|:--:|:-----|:----:|:-----|
| A | 关键字 | ✅ | 多个关键字用**英文逗号**分隔，如 `懒人规则,懒人配置` |
| B | 标识块 | ✅ | `HTML` / `MarkdownV2` / `GraphicMessage` / `VideoMessage` |
| C… | 内容块 | ✅ | 可填多列，**会分条连续发送**，单块建议 ≤ 1024 字 |

> 数据从第 4 行开始（前 3 行为表头）。

**HTML 模式**

标签仅支持 [官方文档](https://core.telegram.org/bots/api#html-style) 里列出的：
`<b>` `<i>` `<u>` `<s>` `<code>` `<pre>` `<a>` `<blockquote>`

`<a>` 标签有简写支持：整行写 `<a>https://example.com</a>` 会自动变成可点击链接。

**MarkdownV2 模式**

按 [官方要求](https://core.telegram.org/bots/api#markdownv2-style) 书写。
⚠️ MarkdownV2 对特殊字符转义要求严格（`_ * [ ] ( ) ~ \` > # + - = | { } . !` 都要转义），填错会**整条消息发送失败**。

**GraphicMessage / VideoMessage 模式**

| 列 | 内容 |
|:--:|:-----|
| C | 图片/视频的 **file_id** 或 URL，多条按**换行**分隔 |
| D | 跟随的说明文字（MarkdownV2 格式） |

> 获取文件 ID：把图片/视频发给机器人 → **回复该消息** → 发送 `/file`
>
> 也可以直接对图片/视频**添加说明文字** `#photoid` 或 `#videoid`（兼容官方版用法）
>
> ⚠️ 官方建议使用 file_id 而非 URL，性能更佳。

> 💡 修改后发送 `/reload` 立即生效，否则默认 3 小时缓存过期。

##### ③ authority_management —— 权限控制表

| 行 | 内容 |
|:--:|:-----|
| 第 3 行 | **群组屏蔽列表** —— 从 B 列起填群组 ID，这些群的消息**不推送**给主人 |
| 第 4 行 | 管理员列表（⚠️ 已废弃，**无需填写**） |

> 群组 ID 以 `-` 开头（超级群通常是 `-100` 开头）
>
> 管理员权限**已改为通过官方接口自动获取**，机器人会实时判断发送者是不是群管理员，
> 不再需要手工维护列表，也不会出现"管理员换了但列表没更新"的问题。

##### ④ sensitive_words —— 敏感词库

| 列 | 类型 | 触发行为 |
|:--:|:-----|:---------|
| A | **绝杀词** | 立即删除消息 + **永久封禁**该用户 + 清理其近期消息 |
| B | **敏感词** | 删除消息 + 警告；3 小时内累计 3 次自动封禁 |

> 数据从第 3 行开始（前 2 行为表头）。
>
> **直接填明文即可**，系统会以 Base64 存储（防误读，**不是加密**）。

**动态管理**（Bot 主人私聊机器人）：

```
/word add 广告词 sensitive    添加敏感词
/word add 诈骗 ban            添加绝杀词
/word del 广告词 sensitive    删除
/word list                    查看当前词库
```

**抗绕过能力**：检测时会跳过空格、`-`、`@`、`#`、各种中英文标点等干扰字符，
所以 `违 禁 词`、`违-禁-词`、`违@禁@词` 都能命中。
但在词中间插入**普通字母数字**不会命中（避免"好"这类短词过度拦截）。

> ⚠️ 短词（≤ 2 个字符）在关键字回复里要求**完全相等**才触发，防止误触。
>
> ⚠️ 词库建议控制在 2000 条以内。系统会把编译结果缓存起来，
> 只有词库变化时才重建，不会每条消息都重新扫描。

##### ⑤ chat_settings —— 群级功能开关 🆕

> 每个群独立配置，由 `/manage` → 功能开关面板读写。**无需手工编辑。**

| 列 | 字段 | 说明 |
|:--:|:-----|:-----|
| A | 会话ID | 群组 ID |
| B | 设置项 | `filter` / `autodelete` / `welcome` / `left` / `verify` / `antiflood` / `rules` |
| C | 值 | `on` / `off`，或文字内容（`rules`） |
| D | 更新时间 | 自动写入 |

**设置群规**（会显示在 `/rules` 和 `/pin` 里）：

```
/settings rules 1. 禁止广告
2. 禁止刷屏
3. 友善交流
```

##### ⑦ error_log —— 错误日志 🆕

| 列 | 字段 | 说明 |
|:--:|:-----|:-----|
| A | 时间 | |
| B | 位置 | 如 `cmd:weather`、`tg:sendMessage`、`task:deleteMessage` |
| C | 错误信息 | |
| D | 上下文 | 相关参数（截断 400 字） |

> 同一个错误 **5 分钟内只记录一次**，避免刷屏撑爆表格。

##### ⑧ task_queue —— 任务队列 🆕

> 这是 ProVersion 最重要的一张表 —— 它取代了官方版"20 个时间触发器"的方案。

| 列 | 字段 | 说明 |
|:--:|:-----|:-----|
| A | 状态 | `pending` / `done` |
| B | 执行时间 | unix 时间戳（秒） |
| C | 类型 | `deleteMessage` / `verifyTimeout` / `unmute` |
| D | 参数 | JSON |
| E | 创建时间 | |
| F | 完成时间 | |

**工作原理**

```
消息发出 → 写入一行任务（执行时间 = 现在 + 60s）
        ↓
每分钟触发一次的调度器 runScheduler()
        ↓
取出所有到期的 pending 任务
        ↓
★ 把同一会话的删除请求合并成一次 deleteMessages 批量调用
        ↓
标记为 done
```

> **对比官方版**：官方版为了同样的效果，给每条消息创建一个一次性时间触发器。
> GAS 普通账号硬限制每个项目最多 **20 个**触发器，于是只能用"数触发器数量 →
> 超了就把最老的提前执行 → 再补建"这套逻辑硬扛，并发一高就丢任务
> （README 里那条 *"受限于GAS，高并发仅支持20次/30s"* 说的就是这个）。
>
> 现在触发器数量**恒为 1**，任务数量上限只取决于表格行数。

##### ⑨ channel_watch —— 频道监听规则表 🆕

> 支撑 `/ch add|del|key|on|off|list|test|log` 这套频道监听能力。
> 一般不需要手工编辑，用 `/ch` 指令维护即可。

| 列 | 字段 | 说明 |
|:--:|:-----|:-----|
| A | 频道ID | 形如 `-1001234567890`，也接受 `@username` |
| B | 频道名称 | 用于卡片展示；从转发消息识别时自动填 |
| C | 推送目标 | 会话 ID，多个用逗号分隔；**留空 = 推送给 Bot 主人** |
| D | 关键词 | 英文/中文逗号、竖线、空格分隔；**留空 = 该频道每条新帖都推** |
| E | 状态 | `on` / `off` |
| F | 备注 | 自由填写 |
| G | 添加时间 | |

**推送判定逻辑**

```
频道新帖 → 逐条规则比对
            ① 频道 ID 是否匹配？
            ② 规则是否 on？
            ③ 正文是否命中关键词？（留空 = 直接命中）
          ↓ 全部通过
        对每个推送目标：先查去重缓存（频道+消息ID+目标，默认 30 分钟窗口）
          ↓
        发一张「频道动态」卡片（标明命中的关键词 + 查看原帖 + 暂停监听按钮）
          ↓
        帖子带媒体时，额外 copyMessage 把原图/视频原样搬过去
```

> ⚠️ **前提条件**：Telegram 只把频道的 `channel_post` 推给**该频道的管理员**。
> 机器人只有在被设为频道管理员**之后**才能收到新帖 —— 在此之前的历史消息它根本没见过，
> 所以 `/ch log` 查不到加管理员之前的帖子。

> 🛡 **防刷爆**：一条新帖最多推给 5 个目标（`CONFIG.channel.maxPushPerPost`）。
> 规则写错时只会少推，不会把自己刷爆。
